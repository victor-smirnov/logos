# S0–S7 gap audit — cluster diagnoses (2026-10-01)

Read-only diagnoses of the 39 interaction clusters (docs/audit/2026-09-26-feature-interactions.md) that are tagged with a closed ADR 0030 step and still differ from rustc 1.98.1 on logosc 0.52.0-preview+main-g858f4e57. Re-measure script: representatives of tests/interactions/clusters/<key>/ against their .rs twins (stdout + exit). The state of each item is kept in docs/adr/0030-hir-core-layer.md, section "S0–S7 gap audit".

## `collect-into-result-option` — owner outside-stdlib

- observed: Logos refuses `opts.iter().cloned().collect::<Option<Vec<i32>>>()` ('Option' does not implement Clone / FromIterator), `.sum::<Result<i64,_>>()` (Result not Sum) and `iter().flatten()` (no method); rustc prints None / Ok(9) / [1, 3]
- minimal repro: `/tmp/claude-1004/triage4/c4.logos: `let a: Option<i32> = Some(1); a.clone()` -> 'receiver is not a struct (got Option)'; c5.logos: `vec![Some(1),None].into_iter().collect::<Option<Vec<i32>>>()` -> Option does not implement FromIterator; c3.logos Result Sum; c2.logos flatten. rustc twin c1.rs: None / Some(1) / Ok(9) / [1, 3]`
- root cause: The library is missing impls. The compiler is fine: a user `impl<T: Clone> Clone for MyOpt<T>` works (c6.logos). stdlib/lang/option/option.logos and stdlib/lang/result/result.logos have no `impl<T: Clone> Clone for Option<T>` or Result<T,E>. stdlib/mem/collections/vec/vec.logos has only `FromIterator<Result<T,E>> for Result<Vec<T>,E>`, with no Option<Vec<T>> twin. stdlib/lang/iter/iter.logos has Sum/Product impls only for i32/i64 (plus &), none for Result/Option. Iterator::flatten does not exist.
- why outside-stdlib: The inference and trait machinery handle these shapes when an impl exists. The failures are missing stdlib items, not a missed S7 rule. Exception: Iterator::flatten needs `Item: IntoIterator` with an `I::IntoIter` projection, so it waits for S9a (Rust-shaped Iterator { type Item }).
- fix / what the owner must provide: stdlib, about 60 lines: Clone for Option<T>/Result<T,E> (match *self, clone the payload), about 16; `impl<T> FromIterator<Option<T>> for Option<Vec<T>>` mirroring the Result one, about 18; `impl<T: Sum<T>, E> Sum<Result<T,E>> for Result<T,E>` (and Product, and Option) by draining into a Vec<T> and then T::sum(v.into_iter()), about 25. Regenerate abi/logos.abi. Leave flatten as an S9a row.

## `deferred-let-no-type-parse` — owner S7

- observed: `let k; k = 5i64; println!("{}", k);` gives a syntax error in Logos; rustc prints 5
- minimal repro: `/tmp/claude-1004/triage4: `fn main() { let k; k = 5i64; println!("{}", k); }` -> syntax error near 'fn' (rustc twin d1.rs prints 5). `let k: i64; k = 5;` works, and so does `let mut o = None; o = Some(2i64);``
- root cause: tools/peg_gen_cpp/grammars/logos.peg let_stmt has `let [mut] IDENT : T ;` but no `let [mut] IDENT ;` (or `let [mut] #IDENT ;`). Behind it, sema_stmt.cpp (the LET lowering, `else if (ann)` / `else { error("let '{}': missing value") }` branch) has no case for a let with neither an annotation nor an initializer. It should take a fresh inference variable: mint_infer_var_ already exists and is how `Vec::new()` / `None` lets get typed later.
- why S7: S7 C-INF already owns local inference variables (mint_infer_var_ / infer_unify_, solved by a later use and E0282 at fn close). An untyped deferred let is exactly an open ?iN on a declared-uninit binding. The grammar alternative is the trivial half, and the audit tags it grammar+S7.
- fix / what the owner must provide: Grammar: add `KW_LET KW_MUT IDENT SEMI` and `KW_LET IDENT SEMI` producing { CODE: LET, [IS_MUT], NAME } (4 lines). Sema: in the no-ann/no-value branch, set `rhs_type = mint_infer_var_("let x")` and do `decl_uninit_vars_.insert(name)` like the annotated path (about 6 lines). Check that lower_assign unifies a bare ?iN target, then test the if/else-assignment members. Total about 10-15 lines.

## `generic-typevar-leaks-to-codegen` — owner S7

- observed: `map_opt(Some(5i64), |x| x * 10)` fails in mlir_gen (unknown enum 'Option__T'); the smaller `ap(5i64, |x| x * 10)` with `F: Fn(T) -> i64` compiles and prints garbage (110173168305136) where rustc prints 50
- minimal repro: `/tmp/claude-1004/triage4/g5.logos: `fn ap<T, F: Fn(T) -> i64>(o: T, f: F) -> i64 { f(o) } fn main() { println!("{}", ap(5i64, |x| x * 10)); }` -> WRONG output (rustc g5.rs: 50). With U in the return: g6 says "operator '+': type mismatch (T vs i64)" and g7 says "expected i64, got T" (the closure param is typed with the callee's own T). With the closure param annotated, `|x: i64|`, it is OK.`
- root cause: sema_expr.cpp, free-function call path in lower_call (`closure_hint_for` lambda plus the arg loop that follows): the closure hint is built from the Fn-bound's raw `b.fn_params` and replaces arg_shape. It is never substituted with the bindings the earlier arguments already fixed (T := i64 from arg 0); only `ret_binds` from the expected type feed formal_shape_. The method-call path (sema_expr.cpp near closure_hint_from_fn_bound use, 'closure's hint can take bindings an EARLIER argument fixes') does this correctly. So the closure is lowered with param type TypeVar 'T' from another scope, and that reaches mlir_gen ('no MLIR type for TypeVar T' is only a warning, and g5 miscompiles silently). Member pairs-14_25 (`impl Fn(A)->B` args to compose) and pairs-9_20 (`count2(vec![..], |x| x > 1)`) have the same mechanism. Member pairs-9_19 is a DIFFERENT defect: a generic `I: Iterator<i64>` body calling `it.map(closure)` SIGSEGVs in Mono::subst_type <- Mono::clone_fn <- drain_method_worklist (h1/h4.logos), likely S8/S9 trait-method-on-type-param identity. It should get its own row.
- why S7: C-EXP 2e ('a closure literal reads the shape') is declared done, but the shape the free-call path hands the closure is the unsubstituted formal. Arguments left to right, substituted by earlier arguments' solutions, is rustc's expected-inputs rule, which S7 owns. No S8 machinery is needed: the callee is already singled out (hint_fi).
- fix / what the owner must provide: In lower_call's arg loop: after lowering arg i, unify hint_fi->param_types[i] with expr_type(arg) into a running SemaSubst (seeded from ret_binds). Run closure_hint_for's result through formal_shape_/subst with that map before using it as arg_shape. As a guard, an unresolved callee TypeVar on a closure param should ICE or diagnose rather than reach mlir. About 15 lines. Add fixtures g5 (stdout compare), g6, and pairs-9_20.

## `open-range-for-head-parse` — owner outside-grammar

- observed: `for i in 0.. { if i > 5 { break; } n += i; }` gives a syntax error in Logos; rustc prints 15. The parenthesised `for i in (0i64..)` parses but loops zero times (prints 0)
- minimal repro: `/tmp/claude-1004/triage4/r1.rs twin (`for i in 0.. {..}` -> 15). In Logos, `for i in 0.. {}` is a syntax error, and r2.logos `for i in (0i64..) {...}` prints 0`
- root cause: tools/peg_gen_cpp/grammars/logos.peg for_stmt has dedicated `expr_ns DOTDOT expr_ns block_body` / `DOTDOTEQ` alternatives and a FOR_EACH `expr_ns block_body` alternative. There is no `expr_ns DOTDOT block_body` form, and expr_ns (log_expr_ns) has no range level, so a half-open head cannot parse. Once it parses (parenthesised), the loop is empty for the reason in rangefrom-iterator-empty (sema RANGE_EXPR with a missing RHS).
- why outside-grammar: The failing layer is the parser's `for` head, which no ADR 0030 step changes. S10 rewrites the `for` semantics (IntoIterator lang items) but not the grammar, so this is not an S8+ wait. It should land in the same commit as the L0 fix in rangefrom-iterator-empty; on its own it would produce a silent empty loop.
- fix / what the owner must provide: The later step must provide a grammar alternative before the plain FOR_EACH alt: `KW_FOR (IDENT|pattern) KW_IN range_from_ns block_body` with `range_from_ns <- expr_ns DOTDOT => { CODE: RANGE_EXPR, LHS: $1 }`, emitted as FOR_EACH ITER (4-6 lines). It depends on the L0 RangeFrom lowering.

## `rangefrom-iterator-empty` — owner L0

- observed: `(5i64..).next()` is None and `(5..).take(3).collect()` is [] in Logos; rustc gives Some(5) and [5, 6, 7]
- minimal repro: `/tmp/claude-1004/triage4/r1.logos: `let mut r = 5i64..; println!("{:?}", r.next());` prints None (rustc r1.rs: Some(5)). r3: `(5i64..).take(3).collect::<Vec<i64>>()` prints []`
- root cause: sema_expr.cpp lower_expr `case la::RANGE_EXPR`: `auto hi = expr.has_key(la::RHS) ? lower_expr(..) : error_expr();`. A missing bound becomes error_expr() with no diagnostic. The integer checks skip Kind::Error, and the code always calls range_i32/range_i64(lo, <error>), giving an empty Range. It is a silent wrong value, a permissive look-alike. stdlib/lang/range/range.logos already has RangeFromI32/I64, range_from_i32/i64 (Iterator impls) and RangeTo/RangeFull carriers, but RANGE_EXPR never selects them. A missing LHS (`..h`, `..`) as a value has the same hole.
- why L0: Range construction is a lang-item lookup: the RANGE_EXPR lowering already goes through stdlib_range_cands with call_pkg_qualifier_ = logos.lang.range. L0 (lang items where the compiler asks) is declared done, but the open-ended members of the Range family were never wired. No S8+ machinery is needed; S10 only changes `for` over it.
- fix / what the owner must provide: In case RANGE_EXPR: with no RHS and not inclusive, call stdlib range_from_i32/i64(lo) (width from lo). With no LHS, call range_to_* or the RangeFull ctor (value position only; the index path at the INDEX_READ RANGE_EXPR special case stays). For an impossible combination (`a..=` with no end), raise error(), never error_expr() silently. About 25 lines. Fixtures r1/r3 and pairs-13_5 (stdout compare); this is also the runtime half of open-range-for-head-parse.

## `closure-param-from-generic-bound-sibling` — owner S7

- observed: `apply2(&mut k, |v| *v += 1)` with `fn apply2<T, F: Fn(&mut T)>(x:&mut T, f:F)` is refused ('cannot move out of v' / 'expected T, got u32'); rustc accepts and exits 5. Worse, a variant compiles and MISCOMPILES: `fn ap<T,F:Fn(T)->T>(x:T,f:F)->T{f(x)}; ap(3u32,|v| v+1) as i32` gives run=208 (rustc 4); `ap(3i64,|v| v*1000000000000)/1000000000000` gives run=96 (rustc 3).
- minimal repro: `package p; fn ap<T, F: Fn(T) -> T>(x: T, f: F) -> T { f(x) } fn main() -> i32 { let r = ap(3u32, |v| v + 1); return r as i32; }  -> Logos run=208, rustc twin exit 4. Refusal form: `fn apply2<T, F: Fn(&mut T)>(x:&mut T, f:F){f(x);}  apply2(&mut k, |v| { *v = 7u32; })` -> 'assignment to *v: expected T, got u32'; rustc OK. The dyn form (pairs-11_38): `fn ap<A,T>(a:A,t:T,f:&dyn Fn(A,T)->A)->A`, `ap(1i64,2i64,&|a,x| a*10+x)` -> 'expected dyn Fn(i64,i64)->i64, got &|<error>,<error>|'; rustc prints 12. The pairs-14_39 member of generic-inference-through-deref-coercion (`sum_by(&d, |x| *x*2)` with `F: Fn(&T)`) has the same root.`
- root cause: In sema_expr.cpp::SemaChecker::lower_call the per-argument shape loop builds `closure_hint_for(i)` from the RAW bound `b.fn_params` / `b.fn_ret`. `formal_shape_` uses only `ret_binds`, which come from the call's expected type. Neither one sees the type params that earlier arguments already bound (T := u32 from `x`). So the closure literal's param gets the bare TypeVar `T`. A non-generic `main` then carries an unresolved TypeVar that nobody refuses, and codegen emits garbage. The method-call path (lower_method_call's `lower_arg_with_hint`) already does this left-to-right: it unifies each non-closure arg into `hint_subst` and calls `closure_hint_from_fn_bound(pt, type_params, hint_subst)`. The free-function path is a second copy that never got that step.
- why S7: This is C-EXP/C-INF: the expected type (shape) of a call argument comes from a generic formal instantiated with what is already inferred. S7 declares 'a closure literal reads the shape' done (690ef983a), yet the free-call arm builds the shape without the sibling-argument bindings. It needs no method probe or trait machinery: the callee is a plain free function, already resolved as `hint_fi`.
- fix / what the owner must provide: In SemaChecker::lower_call's argument loop, keep a `SemaSubst arg_binds` seeded from `ret_binds`. After lowering each argument whose type is not a closure or fn-value, unify `hint_fi->param_types[i]` against `expr_type(arg)`, defaulting IntLit/FloatLit as lower_arg_with_hint does, and add the new bindings. Then compute `arg_shape = formal_shape_(pt, type_params, arg_binds)` and the closure hint via `closure_hint_from_fn_bound(subst(pt), hint_fi->type_params, arg_binds)`, and delete the private `closure_hint_for` lambda. That covers the `&dyn Fn(A,T)` formal too, because formal_shape_ then substitutes A and T. About 25 lines. Also, guarding against the miscompile class: a closure param type that still holds a TypeVar of the CALLEE inside a non-generic body should be refused (or raise an ICE), not lowered. About 10 lines at lower_closure_expr's param typing.

## `const-N-not-inferred-from-array` — owner S7

- observed: `struct V<const N:i64>{c:[i64;N]}; let a = V{c:[1i64,2,3]}; a.n()` aborts with an ICE: 'borrow check: callee of method call .n(..) (V__n__g__ref_V$G1$N) not resolved'. Without the method, mlir_gen fails with 'unknown struct V$G1$<error>'. rustc prints 3. With `let a: V<3> = ...` it works (run=3).
- minimal repro: `package p; struct V<const N: i64> { c: [i64; N] } fn main() -> i32 { let a = V { c: [1i64, 2, 3] }; return a.c[2] as i32; }  -> mlir_gen internal 'unknown struct p.V$G1$<error>', cc=1; rustc twin exit 3. Second shape (pairs-5_49): `fn g<const N: usize>(a:[i64;N])->usize{N} fn f<const N: usize>(a:[i64;N])->usize{ g(a) }` -> 'call to g: could not infer all type arguments'; rustc OK.`
- root cause: (a) sema_expr.cpp::SemaChecker::lower_struct_lit infers struct type args with a PRIVATE unifier: the `[T; N]` branch plus the `unify_field_tv` lambda. Both bind only TypeVars at elem/pointee/type-arg/closure positions and never look at `arr_size_var()`, so a const param that appears only as an array length is never inferred. It falls through to `error_t()`, and the struct instance becomes `V<<error>>`. The shared `unify_types` (sema_expr.cpp, `case Kind::Array`) does bind it, so `g([1,2,3])` works. (b) In unify_types' Array case the bind needs `actual_norm.arr_size_var().empty()`. A symbolic actual length (`[i64; N]` inside a `<const N>` body, as in a recursive or forwarding call) binds nothing, and infer_type_args reports 'could not infer'.
- why S7: This is C-INF, generic-argument inference. S7 claims one argument-to-formal unification (unify_arg_ / unify_types), yet lower_struct_lit keeps its own copy that does not carry the const-length rule, and unify_types has no symbolic-length arm. Both are inference holes that need no resolution or trait machinery.
- fix / what the owner must provide: (a) In lower_struct_lit, replace the special-case `[T; N]` branch and `unify_field_tv` with the shared unification: `unify_types(raw_ft, expr_type(fval), inferred_tmp)`, keeping the existing 'only the struct's own params' and IntLit-default filters. Or, at minimum, bind `TypeRef(raw_ft).arr_size_var()` to an IntLit carrying `const_val = arr_size()` (or to the actual's size var) whenever it names a struct param. About 15 lines. (b) In unify_types `case Array`, when `!actual_norm.arr_size_var().empty()` and it is not an ARR_LEN_EXPR_PFX expression, bind `asv` to a ConstVar/TypeVar named `actual_norm.arr_size_var()`, which is the generic-context identity binding. About 8 lines.

## `generic-inference-through-deref-coercion` — owner S7

- observed: `fn cnt<T>(xs:&[T])`, `cnt(&v)` with `v: Vec<i32>` -> 'call to cnt: could not infer all type arguments'. `fn len<T>(l:&L<T>)` with `len(t)`, `t: &Box<L<T>>` -> same. rustc accepts both (deref coercion against `&[?T]` / `&L<?T>`). The concrete formal `fn cnt(xs:&[i32])` and the turbofish form `cnt::<i32>(&b)` both work.
- minimal repro: `package p; use logos.mem.collections.vec; fn cnt<T>(xs: &[T]) -> i64 { return xs.len() as i64; } fn main() -> i32 { let v: Vec<i32> = vec![1, 2, 3]; return cnt(&v) as i32; }  -> refused; rustc twin exit 3. Box form: `struct W<T>{x:T} fn g<T>(l:&W<T>)->i32{7}  g(&Box::new(W{x:1i32}))` -> refused; rustc exit 7.`
- root cause: sema_expr.cpp::SemaChecker::infer_type_args unifies each argument through unify_arg_ -> unify_types(formal, actual). For `&[T]` against `&Vec<i32>` (or `&W<T>` against `&Box<W<i32>>`), the pointee heads differ (Slice vs Struct Vec, Struct W vs Struct Box) and nothing binds. The deref walk exists only in SemaChecker::try_deref_coerce, which runs after inference, on the already-substituted (concrete) formal. So T is never inferred, and the coercion that would have fixed the types never gets its turn.
- why S7: This is C-INF. rustc infers through coercion: the argument is coerced to the expected `&[?T]` and then unified. The deref/unsize coercion machinery (S4, try_deref_coerce / emit_generic_deref_step) already exists. What is missing is consulting it inside the one argument-to-formal unification that S7 owns. No method probe or trait-obligation solving is needed beyond the Deref target that is already computed.
- fix / what the owner must provide: In unify_arg_ (or in infer_type_args' fixed-param loop), add a step for the case where formal and actual are both Ref/MutRef and `unify_types` bound nothing new while the pointee head constructors differ. Walk the actual pointee's deref chain at the type level (refs, the builtin Box, stdlib Deref targets such as Vec<T>->[T] and String->str; the same steps try_deref_coerce takes, with mutability respected) and unify the formal pointee against the first step whose head matches. A type-only helper `deref_step_type(TypeRef, bool want_mut)` factored out of emit_generic_deref_step avoids building speculative LIR. About 30-40 lines. try_deref_coerce then performs the actual coercion as it does today.

## `partial-move-array-len-accepted` — owner S5

- observed: `let [a, _] = arr; arr.len()` is accepted and runs; rustc gives E0382 'borrow of partially moved value'. It is worse than partial: `let b = arr; arr.len()` (a FULL move) is also accepted, where rustc gives E0382. Every other use of `arr` after the move (`&arr`, `arr[1]`, `arr.iter()`, `let b = arr`) is correctly refused.
- minimal repro: `package p; use logos.mem.string; fn main() -> i32 { let arr = [String::from("p"), String::from("q")]; let b = arr; return arr.len() as i32; }  -> run=2; rustc E0382.`

## `null-mut-generic-field` — owner S7

- observed: In `fn mk<T>() -> G<T> { G { p: null_mut() } }`, Logos reports "call to 'null_mut': could not infer all type arguments". `let p: *mut U = null_mut()` in the same body compiles. `take::<U>(null_mut())` fails the same way, while `take::<i64>(...)` and `G::<i64>{..}` compile. ## `range-index-only-slice-array` — owner S6

## `temp-receiver-or-place-base-not-dropped/fmt-arg-temp-scope` — owner R0

- observed: pairs-9#18 (second rep of the same cluster, separate root): `println!("{}", D::mk().get())` prints 'drop 7' BEFORE '7'. rustc prints '7' then 'drop 7': format_args temporaries live to the end of the enclosing statement. A plain `let x = D{..}.get();` already matches rustc.

Fixture: pairs-9#18 and the minimal repro above, plus a write!/format! variant.
