## Discussion

- 2026-10-10 (Victor), history. Original idea: a systems language without C++'s fundamental problems (UB, metaprogramming, memory safety), with strongly simplified syntax (down to having no expressions), and a developed type system up to dependent types. Goal: derive as many program properties as possible at compile time (Rust), not at run time (Python).
- 2026-10-10 (Victor), what changed along the way: (1) current models no longer need syntactic simplicity; they handle complex and even ambiguous syntax fine. (2) A human is better served by a syntactically expressive language. (3) Rust was chosen as the language where affine types are already worked out. (4) Modern Rust turned out to be syntactically quite complex, in Victor's view more complex than C++. (5) Plus the accumulated influence of the code base. (6) A clear trend: humans will no longer write in programming languages, so developing syntax toward fewer keystrokes makes no sense; humans will not press those keys anyway.
- 2026-10-10 (Victor), summary: Rust was chosen for its worked-out affine types; its current syntactic variety is a "suitcase without a handle": it has to be carried, it cannot be thrown away, and it is hard to maintain.
- 2026-10-10 (Claude): this corrects chapter 1.1 §3: the reason for Rust is the worked-out semantics of affine types (plus model fluency), not the syntax; the syntax is an inherited cost. The 1.1 table row "model InD → Rust surface" must say so.
- 2026-10-10 (Victor) DECISION, two phases. We will NOT carry the suitcase. Phase 1 (now): a functional clone of the Rust compiler on new principles; syntactic AND semantic compatibility with Rust are kept, because porting functionality is much simpler when there is always something to compare against (rustc as oracle). Phase 2: a revision of syntax and semantics; much will be redone. Syntax most likely simplified, grammar made more consistent; type-system behaviour made more orthogonal and consistent. There is no inherited code base to keep compatibility with.
- Consequence for the chapter: compatibility with Rust is a phase-1 instrument (oracle availability), not a property of the language. The 1.1 wording "Rust = bootstrap language" holds; "carried as an inherited cost" in 1.1 §3 must become "kept in phase 1 as the price of an oracle; revised in phase 2".
- 2026-10-10 (Victor): phase-2 design questions are still OPEN (relation to the roadmap stages, the oracle in phase 2, the fate of the imported rustc corpus). Possibly there will be no radical syntax simplification, but also no new borrowings from Rust.
- Consequence for the chapter: state phase 2 as a direction with open questions; the firm part is "no new borrowings from Rust after phase 1"; the extent of simplification is undecided.
- 2026-10-10 (Victor), the main differences from Rust. (1) Direct and full support of homoiconic compile-time metaprogramming (Metaprog). (2) Integration into the language AND the compiler of a lightweight object format with zero serialization for external memory (Writ); it lets programs and metaprograms exchange structured data. The whole compiler is built on it internally: internal representations are on Writ; the compiler works on the fixpoint principle and uses a Datalog-compatible compilation mechanism, so it can be written in Datalog (which is already being done).
- 2026-10-10 (Victor), consequence: Logos was NOT built on rustc; the compiler was written from a clean slate. C++ was chosen because of MLIR; otherwise Rust would have been the reasonable implementation language. No complaints about C++ now; the compiler will be rewritten in Logos later. The full reimplementation did delay the project.
- 2026-10-10 (Claude): code anchors for these claims: AST and L-IR as Writ arenas (System map §3.2, internals/multi-arena-ir.md); quotes/antiquotes and host functions logos_emit_source, logos_quote_expr_subst in src/compiler/main.cpp; metaprog libraries stdlib/mem/compiler/metaprog/; Pending + nested loops in the driver; Datalog rules src/compiler/dl/rules/{polonius,logos_bc}.dl as the default borrow checker; Canon as a Deem program. Chapter placement: 2.1 (differences, why not rustc, why C++), 2.5 (metaprogramming), 3.1 (fixpoint driver), 3.3 (Writ as the compiler's memory). Alternatives for 2.1: build on rustc (rejected: Writ IR, fixpoint driver and homoiconic metaprog need own internals); implement in Rust (rejected: MLIR access); cost: delay.
- 2026-10-10 (Victor), homoiconicity defined: metaprogramming uses the same syntax, the full language, as programming; quoting is the only addition, a specialised extension. Confirmed: the shared representation is Writ, not Lisp-style syntax. (Claude, for the chapter's contrast: Rust has macro_rules as a separate pattern language, proc macros over token streams in a separate crate without types, const fn as a restricted subset; C++ has templates as a separate functional sublanguage; Logos metaprograms are ordinary Logos fns run by metacall over typed Writ AST.)
- 2026-10-10 (Victor), "Datalog-compatible compilation mechanism" confirmed as: monotone accumulation of facts to a fixpoint; unmet demand recorded (Pending) and met later by a producer; stages moved into Datalog rules one at a time (borrow checker first). Stratification and compiler facts as relations (ADR 0032 D6, --emit-facts) are part of the same direction: "all of this will be done". Status split for the chapter: fixpoint + Pending + Datalog BC = LANDED; stratification of the driver and D6 = PROPOSED.
