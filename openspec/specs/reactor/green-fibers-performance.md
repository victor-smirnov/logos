# Green Fibers: Анализ Производительности

## Overhead вызова красного кода из зеленого

### Операции при `__builtin_red_call`

При вызове красной функции из зеленой (`__builtin_red_call`) выполняются следующие операции:

#### 1. Подготовка возвращаемого значения (опционально)
```cpp
// Если возвращаемое значение большое (indirect return)
Address RetAddr = CreateTempAlloca(RetLLVMTy, RetAlign, "red_call.ret");
```
**Overhead**: 
- Для малых типов (int, double, указатели): **0 операций**
- Для больших типов (std::string, большие структуры): **1 аллокация на стеке файбера**
  - Обычно: `sub %rsp, <size>` + выравнивание
  - **~5-10 циклов CPU** (зависит от размера и выравнивания)

#### 2. Сохранение стека файбера
```cpp
llvm::Value *FiberSP = Builder.CreateCall(StackSaveFn);
```
**Генерируемый код** (x86-64):
```asm
callq   llvm.stacksave
mov     %rax, %rbx    ; или другой регистр
```
**Overhead**: 
- `stacksave` обычно инлайнится в простое `mov %rsp, %rax`
- **~1-2 цикла CPU**

#### 3. Загрузка системного стека из TLS
```cpp
llvm::Value *SystemSP = Builder.CreateAlignedLoad(
    CGM.Int8PtrTy, SystemStackVar, CGM.getPointerAlign());
```
**Генерируемый код** (x86-64):
```asm
mov     %fs:0x70, %rax    ; или другой offset для TLS
```
**Overhead**: 
- Доступ к TLS через `%fs` сегмент
- **~3-5 циклов CPU** (зависит от архитектуры, может быть больше на некоторых системах)

#### 4. Переключение на системный стек
```cpp
Builder.CreateCall(StackRestoreFn, SystemSP);
```
**Генерируемый код** (x86-64):
```asm
mov     %rax, %rsp
```
**Overhead**: 
- `stackrestore` обычно инлайнится в простое `mov %rax, %rsp`
- **~1 цикл CPU**

#### 5. Подготовка аргументов и вызов функции
```cpp
CallArgList Args;
EmitCallArgs(Args, FPT, ...);
RValue Ret = EmitCall(CallFnInfo, Callee, RetSlot, Args);
```
**Overhead**: 
- **Такая же, как у обычного вызова функции**
- Аргументы размещаются на системном стеке (не на стеке файбера)

#### 6. Восстановление стека файбера
```cpp
Builder.CreateCall(StackRestoreFn, FiberSP);
```
**Генерируемый код** (x86-64):
```asm
mov     %rbx, %rsp    ; восстановление сохраненного указателя
```
**Overhead**: 
- **~1 цикл CPU**

### Итоговый Overhead

#### Минимальный случай (малые возвращаемые значения)
- Сохранение стека: **~1-2 цикла**
- Загрузка TLS: **~3-5 циклов**
- Переключение стека: **~1 цикл**
- Восстановление стека: **~1 цикл**
- **Итого: ~6-9 циклов CPU**

#### Случай с большим возвращаемым значением
- Все вышеперечисленное: **~6-9 циклов**
- Аллокация на стеке файбера: **~5-10 циклов**
- **Итого: ~11-19 циклов CPU**

### Сравнение с обычным вызовом

**Обычный вызов функции** (red → red или green → green):
- Подготовка аргументов: **~0-2 цикла** (если аргументы уже в регистрах)
- `call` инструкция: **~1-2 цикла** (зависит от предсказания ветвления)
- **Итого: ~1-4 цикла CPU**

### Относительный Overhead

- **Минимальный случай**: `__builtin_red_call` примерно **в 2-9 раз медленнее** обычного вызова
- **С большим возвращаемым значением**: примерно **в 3-19 раз медленнее**

### Оптимизации

#### 1. Инлайнинг `stacksave`/`stackrestore`
LLVM обычно инлайнит эти intrinsic'ы, что минимизирует overhead.

#### 2. Кэширование системного стека
Системный стек загружается из TLS каждый раз. Теоретически можно кэшировать в регистре, но это сложно из-за ABI.

#### 3. Batch вызовы
Если нужно вызвать несколько красных функций подряд, можно оптимизировать:
```cpp
// Вместо:
red_func1();
red_func2();
red_func3();

// Можно сделать:
__builtin_red_call_batch(red_func1, red_func2, red_func3);
```
Но это требует дополнительной реализации.

### Рекомендации

1. **Минимизировать переходы**: Стараться группировать вызовы красных функций
2. **Избегать в горячих путях**: Если функция вызывается миллионы раз, overhead может быть заметен
3. **Профилирование**: Измерить реальный overhead на целевой платформе
4. **Оптимизация больших возвращаемых значений**: Рассмотреть передачу через указатель вместо возврата по значению

### Реальный Overhead (измерения)

На практике overhead может быть выше из-за:
- **Cache misses** при доступе к TLS
- **Pipeline stalls** при переключении стека
- **Branch misprediction** (если LLVM не инлайнит intrinsic'ы)
- **Memory barriers** (если TLS требует синхронизации)

**Ожидаемый реальный overhead**: **~10-30 циклов CPU** для минимального случая, **~20-50 циклов** с большим возвращаемым значением.

### Выводы

Overhead вызова красного кода из зеленого **относительно небольшой** (~10-30 циклов), но:
- Это **в 3-10 раз медленнее** обычного вызова
- Для большинства приложений это **приемлемо**
- В критичных по производительности местах стоит **минимизировать** такие переходы

## Overhead вызова зеленой функции из красной

### Операции при `fiber_context::call()`

При вызове зеленой функции из красной через `fiber_context::call()` выполняются следующие операции:

#### 1. Подготовка стека (опционально, только при первом вызове)
```cpp
ensure_stack();
```
**Overhead**: 
- Проверка `started_`: **~1 цикл**
- Выравнивание указателя стека: **~2-3 цикла**
- Сохранение `fiber_context*` на стеке: **~1 цикл**
- Инициализация `context_frame`: **~1 цикл**
- **Итого: ~5-6 циклов** (только при первом вызове)

#### 2. Создание invocation объекта
```cpp
pending_invocation_ = std::make_unique<detail::invocation<Fn, Args...>>(...);
```
**Overhead**: 
- **Heap allocation** через `std::make_unique` (вызов `new`)
- Размер объекта: `sizeof(invocation<Fn, Args...>)` + размеры аргументов
- **~100-500 циклов CPU** (зависит от размера аргументов и аллокатора)
- Может быть **cache miss** при доступе к heap

#### 3. Сохранение текущего контекста и переключение
```cpp
caller_ = current();  // Получение текущего fiber_context из TLS
switch_to(this);
```

**Операции в `switch_to()`**:
```cpp
// 1. Получение текущего контекста из TLS
fiber_context* previous = green::tls_current_fiber;  // ~3-5 циклов (TLS access)

// 2. Сохранение системного стека (если переходим с системного стека)
asm volatile("movq %%rsp, %0" : "=r"(rsp));  // ~1 цикл
__green_fiber_system_stack = rsp;  // ~3-5 циклов (TLS write)

// 3. Обновление TLS
green::tls_current_fiber = target;  // ~3-5 циклов (TLS write)

// 4. Вызов контекст-свитчера
__green_fiber_context_switch(from, to);
```

**Ассемблерный код `__green_fiber_context_switch`**:
```asm
// Сохранение callee-saved регистров (7 регистров)
mov %r15, 0(%rdi)    // ~1 цикл
mov %r14, 8(%rdi)    // ~1 цикл
mov %r13, 16(%rdi)   // ~1 цикл
mov %r12, 24(%rdi)   // ~1 цикл
mov %rbx, 32(%rdi)   // ~1 цикл
mov %rbp, 40(%rdi)   // ~1 цикл
mov %rsp, 48(%rdi)   // ~1 цикл
lea 0f(%rip), %rax   // ~1 цикл (получение адреса возврата)
mov %rax, 56(%rdi)   // ~1 цикл

// Восстановление регистров из целевого контекста (7 регистров)
mov 0(%rsi), %r15    // ~1 цикл
mov 8(%rsi), %r14    // ~1 цикл
mov 16(%rsi), %r13   // ~1 цикл
mov 24(%rsi), %r12   // ~1 цикл
mov 32(%rsi), %rbx   // ~1 цикл
mov 40(%rsi), %rbp   // ~1 цикл
mov 48(%rsi), %rsp   // ~1 цикл (переключение стека!)
mov 56(%rsi), %rax   // ~1 цикл
jmp *%rax            // ~1-3 цикла (branch, может быть misprediction)
```

**Overhead переключения контекста**:
- Сохранение 7 регистров: **~7 циклов**
- Восстановление 7 регистров: **~7 циклов**
- Сохранение/восстановление rip: **~2 цикла**
- Переключение стека (`mov %rsp`): **~1 цикл** + возможный **cache miss**
- `jmp` с возможным misprediction: **~1-20 циклов** (зависит от предсказателя)
- TLS операции: **~6-10 циклов**
- **Итого: ~24-47 циклов** для переключения контекста

#### 4. Выполнение функции на стеке файбера
**Overhead**: 
- **Такая же, как у обычного вызова** (но на другом стеке)
- Может быть проверка стека (`__morestack`) если стек заканчивается: **~10-50 циклов** (опционально)

#### 5. Возврат результата и переключение обратно
```cpp
// В enter_loop() после выполнения функции:
switch_to(caller_);  // Еще одно переключение контекста
```

**Overhead**: 
- Еще одно переключение контекста: **~24-47 циклов**
- Извлечение результата из `std::any`: **~5-10 циклов** (проверка типа, cast)

#### 6. Освобождение invocation объекта
```cpp
pending_invocation_.reset();  // Вызов деструктора и delete
```
**Overhead**: 
- Вызов деструктора: **~0-5 циклов** (зависит от типа)
- `delete` (освобождение памяти): **~50-200 циклов** (зависит от аллокатора)

### Итоговый Overhead

#### Минимальный случай (малые аргументы и возвращаемое значение)
- Подготовка стека (только первый раз): **~5-6 циклов**
- Создание invocation: **~100-200 циклов** (heap allocation)
- Переключение контекста (туда): **~24-47 циклов**
- Переключение контекста (обратно): **~24-47 циклов**
- Извлечение результата: **~5-10 циклов**
- Освобождение invocation: **~50-100 циклов**
- **Итого: ~208-410 циклов CPU**

#### С большими аргументами/возвращаемым значением
- Все вышеперечисленное: **~208-410 циклов**
- Копирование больших аргументов в invocation: **~50-200 циклов**
- Копирование результата из std::any: **~50-200 циклов**
- **Итого: ~308-810 циклов CPU**

### Сравнение с обычным вызовом

**Обычный вызов функции** (red → red):
- Подготовка аргументов: **~0-2 цикла**
- `call` инструкция: **~1-2 цикла**
- **Итого: ~1-4 цикла CPU**

### Относительный Overhead

- **Минимальный случай**: `fiber_context::call()` примерно **в 50-200 раз медленнее** обычного вызова
- **С большими аргументами**: примерно **в 75-200 раз медленнее**

### Основные источники overhead

1. **Heap allocation для invocation** (~100-500 циклов) — **самый большой источник**
2. **Два переключения контекста** (~48-94 цикла суммарно)
3. **TLS операции** (~12-20 циклов)
4. **Освобождение памяти** (~50-200 циклов)

### Оптимизации

#### 1. Пул invocation объектов
Вместо `std::make_unique` каждый раз, можно переиспользовать объекты:
```cpp
// Пул invocation объектов
static thread_local std::vector<std::unique_ptr<invocation_base>> invocation_pool;
```
**Потенциальная экономия**: ~100-400 циклов на вызов

#### 2. Оптимизация переключения контекста
- Использовать `xmm` регистры для копирования (если доступно): может быть быстрее
- Минимизировать количество сохраняемых регистров (но это может сломать ABI)

#### 3. Inline вызовы для простых случаев
Для функций без аргументов и возвращаемых значений можно избежать heap allocation.

#### 4. Small Buffer Optimization для invocation
Использовать `std::aligned_storage` для малых invocation объектов, чтобы избежать heap allocation.

### Рекомендации

1. **Избегать частых вызовов**: `fiber_context::call()` очень дорогой, не использовать в горячих путях
2. **Группировать работу**: Выполнять как можно больше работы внутри одного вызова зеленой функции
3. **Минимизировать аргументы**: Большие аргументы копируются в heap
4. **Профилирование**: Измерить реальный overhead на целевой платформе

### Реальный Overhead (измерения)

На практике overhead может быть еще выше из-за:
- **Cache misses** при доступе к heap и TLS
- **Pipeline stalls** при переключении контекста
- **Branch misprediction** при `jmp` в контекст-свитчере
- **Memory barriers** (если TLS требует синхронизации)
- **Fragmentation heap** (если много вызовов)

**Ожидаемый реальный overhead**: **~300-1000 циклов CPU** для минимального случая, **~500-2000 циклов** с большими аргументами.

### Выводы

Overhead вызова зеленой функции из красной **значительно выше**, чем вызов красной из зеленой:
- **В 50-200 раз медленнее** обычного вызова
- Основной источник — **heap allocation** для invocation объекта
- Это **не подходит** для частых вызовов в горячих путях
- Рекомендуется **группировать работу** внутри зеленых функций

## Overhead вызова зеленой функции из зеленой (Green → Green)

### Операции при обычном вызове green → green

При вызове зеленой функции из зеленой выполняется **обычный call**, но с дополнительной проверкой стека в прологе вызываемой функции.

#### 1. Обычный call
```asm
call green_function
```
**Overhead**: 
- **Такая же, как у обычного вызова** (red → red)
- Подготовка аргументов: **~0-2 цикла**
- `call` инструкция: **~1-2 цикла** (зависит от предсказания ветвления)
- **Итого: ~1-4 цикла CPU**

#### 2. Проверка стека в прологе green функции

LLVM добавляет проверку стека в начало каждой green функции (из-за `split-stack` атрибута):

**Генерируемый код** (x86-64):
```asm
green_function:
    # Проверка: достаточно ли стека?
    mov     %rsp, %rax              ; Сохранить текущий указатель стека
    cmp     %fs:0x70, %rax         ; Сравнить с stack_limit в TLS
    jae     .enough_stack           ; Если достаточно, пропустить выделение
    
    # Недостаточно стека - выделить новый сегмент
    mov     $frame_size, %edi       ; Размер фрейма
    mov     $arg_size, %esi        ; Размер аргументов
    call    __morestack             ; Выделить новый сегмент
    # __morestack возвращает новый указатель стека в %rax
    mov     %rax, %rsp              ; Переключиться на новый сегмент
    
.enough_stack:
    # Обычный пролог функции
    push    %rbp
    mov     %rsp, %rbp
    # ... остальной код функции
```

**Overhead когда стека достаточно** (обычный случай):
- `mov %rsp, %rax`: **~1 цикл**
- `cmp %fs:0x70, %rax`: **~3-5 циклов** (доступ к TLS)
- `jae .enough_stack`: **~1-2 цикла** (условный переход, обычно предсказывается правильно)
- **Итого: ~5-8 циклов CPU** дополнительно к обычному вызову

**Overhead когда стека не хватает** (редкий случай):
- Все вышеперечисленное: **~5-8 циклов**
- Вызов `__morestack`: **~100-500 циклов** (heap allocation нового сегмента)
- Переключение стека: **~1 цикл**
- **Итого: ~106-509 циклов CPU** (но это редкий случай)

### Итоговый Overhead

#### Обычный случай (стека достаточно)
- Обычный call: **~1-4 цикла**
- Проверка стека в прологе: **~5-8 циклов**
- **Итого: ~6-12 циклов CPU**

#### Редкий случай (недостаточно стека)
- Обычный call: **~1-4 цикла**
- Проверка стека + выделение сегмента: **~106-509 циклов**
- **Итого: ~107-513 циклов CPU**

### Сравнение с Red → Red

**Обычный вызов функции** (red → red):
- Подготовка аргументов: **~0-2 цикла**
- `call` инструкция: **~1-2 цикла**
- **Итого: ~1-4 цикла CPU**

### Относительный Overhead

- **Обычный случай** (стека достаточно): green → green примерно **в 1.5-3 раза медленнее** red → red
- **Редкий случай** (недостаточно стека): green → green примерно **в 25-125 раз медленнее** red → red

### Оптимизации

#### 1. Оптимизация проверки стека
LLVM может оптимизировать проверку стека:
- Если функция маленькая и не использует много стека, проверка может быть упрощена
- Если функция большая, проверка обязательна

#### 2. Предсказание ветвления
Условный переход `jae` обычно предсказывается правильно (стека обычно достаточно), что минимизирует overhead.

#### 3. Кэширование stack_limit
`stack_limit` загружается из TLS каждый раз. Теоретически можно кэшировать, но это сложно из-за того, что разные файберы могут иметь разные лимиты.

#### 4. Пул сегментов стека
Как упомянул пользователь, пуллинг сегментов может значительно ускорить выделение новых сегментов (с ~100-500 циклов до ~10-50 циклов).

### Рекомендации

1. **Обычный случай приемлем**: Overhead в 1.5-3 раза не критичен для большинства приложений
2. **Избегать частых выделений сегментов**: Стараться не использовать слишком много стека в одной функции
3. **Пул сегментов**: Реализовать пул сегментов для ускорения выделения
4. **Профилирование**: Измерить реальный overhead на целевой платформе

### Реальный Overhead (измерения)

На практике overhead может быть выше из-за:
- **Cache misses** при доступе к TLS (`stack_limit`)
- **Branch misprediction** (редко, но возможно)
- **Pipeline stalls** при проверке стека

**Ожидаемый реальный overhead** (обычный случай): **~8-15 циклов CPU** для green → green, **~1-4 цикла** для red → red.

### Выводы

Overhead вызова зеленой функции из зеленой **небольшой** (~8-15 циклов в обычном случае):
- Это **в 1.5-3 раза медленнее** обычного вызова (red → red)
- Для большинства приложений это **приемлемо**
- Основной overhead — **проверка стека** в прологе функции
- Редкие случаи выделения нового сегмента **очень дорогие** (~100-500 циклов), но их можно оптимизировать пулом сегментов
